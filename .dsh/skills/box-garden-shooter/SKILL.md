> ⚠️ **两组仍未闭环的验收项 + 两轮"没人看过"的改动，都是环境限制，不是代码问题。**
> **B 打包产物**：`release\win-unpacked\*.exe` 与 NSIS 安装包都不存在——本机受限沙箱既拒绝一切 Chromium / Electron 进程（命名管道 `0x5`），也让 `electron-builder` 的模块收集器 `spawn EPERM`。**D 前序积压**：真机帧率、画面目视、音效听感、真人局时、双端一致性读数**一条都没做**，理由同上（本机拿不到截图，也没有耳朵和手能替）。**阶段 6 / 7 / 8 / 9 / 10 的十三项改动（转身 / 鼠标视角 / 装饰物实体 / 二段跳 / 血条 / 右手枪 / 暂停菜单 / 第一人称视角 / 开镜准心 / 黄色直线弹道 / 十秒空场的倒计时那行字 / 一次 5–10 只的成批投放 / 4800 血的典狱长）同样一次都没被人看过**——它们的判据都是"看一眼"或"打一局"，而单测只能证明"接线正确、数值按要求、池子不涨、坐标在右手边、两种模式弹道逐位相同、发射后方向逐位不变、前 10 秒场上确实没人"，证明不了"好看"与"躲得掉"，也证明不了"这版还能不能玩"。**第一人称尤其如此**：它的枪位（`VIEW.firstPersonWeapon` 六个数）是**纯靠推算摆出来**的几何，而它最大的反馈是"身体消失了"——**消失没有画面可以断言**。

## 1. Brief（项目简报）

### 1.1 一句话定位

做一个**能立刻上手、单手就能玩明白**的小型 3D 箱庭射击游戏：玩家站在一块被围栏圈起的立体沙盘里，一边用步枪点掉成群扑上来的小敌人，一边等那只慢慢走过来的大块头，然后决定是继续清杂兵还是先把子弹喂给它。

### 1.2 为什么做这个

三个明确目标，按优先级排序：

1. **验证一套可复用的 Three.js 游戏骨架。** 不是做一个 Demo，而是搭出一套"输入 → 固定步长模拟 → 渲染"分层的、可测试的、能直接长出第二个游戏的工程底座。
2. **把"一套代码两端发布"跑通。** Web 端即时可玩、可分享链接；桌面端拿到一个双击就能进的原生窗口。全程同一份 `src/`，差异只允许存在于薄壳层。
3. **用最小的内容量换取最大的可玩性。** 只做两种敌人、两种攻击模组、一张地图，靠**节奏设计**而不是内容堆量来支撑 10–15 分钟的一局。（**阶段 10 起这一局是一份固定脚本**——30 只潜袭者按 5/5/5/5/10 投放，然后一只典狱长，见 §1.3；"10–15 分钟"是 Brief 时代的推算，已被脚本取代，真实局时仍无人量过。）

### 1.3 目标体验

一局游戏的完整情绪曲线：

| 阶段 | 时长 | 玩家感受 | 系统在做什么 |
|---|---|---|---|
| 熟悉 | 0:00–0:10 | "这地方多大？枪手感如何？" | **空场十秒**：屏幕正上方一行 `第一批敌人还有 N 秒到达战场`，N 从 10 数到 1；世界从玩家点进来的那一 tick 才开始走（§4.31） |
| 升温 | 0:10–0:30 | "它们在包我，得动起来" | 第 1 / 2 批各 5 只，相隔 10 秒；每具身体落地前 0.9 s 有地面预警环 |
| 压力 | 0:30–0:60 | "弹药有点紧，注意换弹时机" | 第 3 / 4 批各 5 只，**第 5 批一次 10 只**——全场累计恰好 **30 只** |
| 转折 | 清场之后 | "大块头来了，杂兵已经清完" | **场上清空**才下单典狱长（**只此一次，没有超时兜底**；不清完就永远见不到它），`field:cleared` 顺手补 1 个投掷充能（`ITEMS.chargesPerClear`） |
| 收束 | 典狱长登场后 | "先挪出这条线，再打它的弱点" | **4800 血的弱点战**：躯干流打不完这一局的弹药，必须瞄头；打死它即 `VICTORY` |

> **一局的形状是一份固定脚本，不是一条曲线**：`DIRECTOR.openingCountdown = 10` / `batchInterval = 10` / `batchSizes = [5, 5, 5, 5, 10]`，投放时刻 t = 10/20/30/40/50 s 是**绝对时刻**（长帧与 hitstop 都不会让它漂）。初版 Brief 那句"10–15 分钟一局"是曲线时代的纸面推算，**已被这份脚本取代**——真实局时仍没人量过（§4.29）。

**核心体验关键词：清晰、紧凑、有节奏。** 不追求拟真，不追求叙事。

### 1.4 核心玩法循环

```
         ┌──────────────────────────────────────────┐
         │                                          │
    观察威胁 ──► 移动/走位 ──► 瞄准(右键) ──► 射击(左键)
         ▲                                          │
         │                                          ▼
    道具投掷(E) ◄── 判断时机 ◄── 弹匣告警 ◄── 换弹(R)
         │                                          │
         └──────────► 敌人减员 ──► 批次推进 ────────┘
```

### 1.5 操作方案（已锁定，不得擅自更改）

| 输入 | 行为 | 备注 |
|---|---|---|
| `W` | 向上 / 向前移动 | 摄像机局部坐标系的 +forward |
| `A` | 向左移动 | 摄像机局部坐标系的 −right |
| `S` | 向下 / 向后移动 | |
| `D` | 向右移动 | |
| **鼠标左键** | 射击 | 按住持续射击（全自动） |
| **鼠标右键** | 开镜瞄准（ADS） | 按住生效；FOV 78°→45°（目标被拉近），移速 ×0.55，扩散 3.4°→0.35°，**准心从扩散锥投影换成更大的瞄准环**（`CROSSHAIR`：腰射下限 6 px → 满 ADS 46 px + 加粗换色，§4.26）。**右键对浏览器没有任何影响**（整页 `contextmenu` 被吃掉），且 ADS 只在指针锁定（在游戏里）时成立（§4.27） |
| `R` | 换弹 | 可打断窗口 0.35s；空仓换弹更快（1.7s vs 2.1s） |
| `E` | 道具投放 | 抛物线投出，1.4s 引信，5.5m 溅射 |
| `Shift` | 疾跑 | 辅助键，用于拉开距离 |
| `Space` | 跳跃（**二段跳**） | 地面一下 = 起跳；**空中再按一下 = 第二段**。空中那一下必须是一次**新的按压**（按住不放只有一段），每两次落地之间最多 2 段（`PLAYER.maxJumps`）；走下台沿会消耗起跳那一次（§4.21） |
| `Esc` | 暂停菜单 | 引擎级释放鼠标 + 弹出**半透明暂停面板** `结束暂停` / `重新开始` / `返回主界面`。**不是起始界面本身**（阶段 7 修的现场反馈，§4.24） |
| `V` | 切换第一 / 第三人称 | 点按切换（不是按住）。**进游戏默认第一人称**（`CAMERA.defaultView`），每次重开也回到第一人称。两种视角**共用同一套弹道判定**，只改相机与枪挂在哪儿（§4.25） |
| **点击面纱** | 开始这一局 | 点的是标题遮罩；**指针锁定成功之后世界才走第一个 tick**（`bootGame().start()` 调 `loop.setPaused(true)`，§4.31）。所以开局那十秒倒计时**不会**在标题页上被吃掉，敌人也不会隔着不透明面纱刷出来 |

> **视角约定**：移动方向始终相对**摄像机朝向**解算，而非角色模型自身朝向。角色模型通过**限速转身**追上移动方向——这是第三人称过肩射击的标准手感，也是"A 键到底是不是向左"这类手感的唯一正确答案。**阶段 6 起这句话才真的成立**：在那之前身体与相机同一个角度、同一帧到位（现场反馈"增加转身的动作"），而且**鼠标压根不能转视角**（`InputState` 的位移折叠写在没人调用的 `update()` 里，见 §4.18）。现在：`player.yaw` 仍是唯一权威（移动与弹道都读它），身体有自己的 yaw，按 `PLAYER.turnRateDegPerSec` 限速追移动方向（站着不动时追相机），并带一点转身倾斜（§4.20）。
>
> **视角模式（阶段 8 起）**：`CameraState.viewMode` 是唯一权威，两种模式的数字全在 `VIEW`（`config.ts`）。`V` 走 `World.toggleView()`（翻转 → **重解瞄准** → snap 相机），**只改基座位置 / 相机后撤距离 / 曳光起点，绝不改 `forward`**——两种模式的 `direction` 与 `fovDeg` 必须逐位相同（§4.25）。
>
> **一局的起点（阶段 10 起）**：`t = 0` 是"玩家点进来、指针锁定成功"的第一个 tick，从那一刻起屏幕正上方显示 `第一批敌人还有 N 秒到达战场`（`#countdown`，预警色，N 从 10 数到 1，到 0 隐藏，`countdownText()`）。这十秒是**空场**——这份固定脚本里唯一的一段缓冲。

### 1.6 敌人设计

#### 小型敌人 `Stalker`（潜袭者）

- **定位**：消耗品式的压力源。单只不可怕，一群就很难看。
- **攻击模组**：**冲锋 + 接触近战**。提速至 9 m/s 扑向玩家，进入 1.5m 触发 0.42s 抬手动作，命中造成 9 点伤害，随后 0.55s 硬直。
- **视觉读条**：抬手时躯干前倾 + 体表发光；这是玩家判断"该后撤了"的唯一依据。
- **数值**：HP 60 · 移速 5.2 · 伤害 9 · 冷却 1.1s · 弱点倍率 ×2.8
- **设计意图**：60 HP 意味着**躯干 3 枪 / 爆头 1 枪**（`22 × 2.8 = 61.6 ≥ 60`；仅 22m 内满伤时成立）。爆头奖励必须足够大，否则玩家没有理由去瞄。
  > 倍率是 **2.8 而非 2.5**，这是技术方案 §6.3 决策 D6 的结论——2.5 只有 55 点，要 2 枪。**不要改回 2.5。**

#### 大型敌人 `Warden`（典狱长）

- **定位**：节奏破坏者。它不追你，它从远处用**一条线**把你从掩体后面逼出来。
- **攻击模组**（**阶段 9 起：一条黄色直线，不再是三发区域轰炸**）：26m 内进入攻击；1.35s 长抬手，抬手期间从它身上拉出一条**黄色瞄准线**指向玩家胸口并逐帧跟着玩家走（最后 0.35s 快闪）；抬手结束时**方向被冻住**，一枚黄色弹丸沿它飞，弹速 24 m/s、命中半径 0.85m、站在线上吃 34 点，冷却 2.8s。线会被**货箱挡下**，并且**只打玩家**（不误伤自己的小兵）。
- **与小型敌人的本质差异**：小型敌人惩罚"站着不动"，大型敌人惩罚"**站在开阔地且不换位**"。两者叠加时，玩家被迫在"挪出这条线"和"清杂兵"之间做取舍——**这就是这个游戏全部的策略深度**（为什么不再预判提前量、为什么弹丸不绑主人的状态机，见 §4.28）。
- **数值**：HP **4800** · 移速 1.9 · 伤害 34 · 冷却 2.8s · 弱点倍率 ×1.6 · 弹速 24 m/s · 命中半径 0.85m · 射程 70m
- **解锁**：**场上清空才下单，一局恰好一次，没有超时兜底**——30 只潜袭者全部结算掉它才出现，**不杀最后一只就永远见不到它**。它在 0.9 s 的投放预警里**还不存在**，所以"下了单"与"到场了"是两个相位（§4.30）。
- **设计意图**：**4800 HP 是一场弱点战**——躯干 `4800 / 22 = 219` 发，而一局总共只带 240 发（弹匣 30 + 备弹 210，30 只潜袭者还要吃掉约 90 发），所以**只打躯干的人在它死之前就没子弹了**；弱点 `4800 / (22 × 1.6) = 137` 发才打得完。击杀它必然需要一次主动换弹，而换弹时它还在输出——这就是压力来源。
  > 阶段 10 按需求把血量从 2400 **翻倍到 4800**（初版 Brief 那句"约 2 个弹匣"的错误口径早在 D7 就被改成按实算写两个口径）。**这是一次有意、且从未被真人试玩的难度步进**：要把它打开回去，调 `WEAPON.reserveAmmo`，**不是**把血量改回去。
- **狂暴阶段**：HP ≤ 35% 时进入 `ENRAGE`。**只压缩收招时间与冷却（×0.75），绝不压缩抬手时间**——抬手是玩家唯一的反应依据，缩短它等于把"难"变成"不公平"。狂暴是**数值修正量**，不是一套新的状态机。

#### 群体攻击的"槽位"约束（小敌人可读性的关键）

小敌人成群时最容易出现的问题是**围攻同时出手**，玩家在 0.5 秒内被 6 只同时打到，感觉是"瞬间暴毙"而不是"我没躲好"。解决办法是给近战攻击加**并发槽位**：

```ts
// 同一时刻最多 ATTACK_SLOTS 只小敌人处于 TELEGRAPH/STRIKE 状态
const ATTACK_SLOTS = 3;
// 未拿到槽位的敌人停在 CHASE 的外围，做出"蓄势"姿态但不出手
```

效果：同时威胁玩家的敌人被限制在 3 只以内，其余在外圈游走等待。玩家的**注意力负担**是恒定的，而被包围的**压迫感**依然完整——这是"人多但不混乱"的标准做法。

#### 投放规则（硬性需求，本项目最核心的一条）

```
一局 = 一份固定脚本（t = 0 是玩家点进来、指针锁定成功后的第一个 tick）
   │
   ├─► t = 0 … 10 s   OPENING    空场；屏幕上数 `第一批敌人还有 N 秒到达战场`
   │
   ├─► t = 10 / 20 / 30 / 40 / 50 s   五批：5 / 5 / 5 / 5 / 10 = 30 只
   │                                  每具身体落地前 0.9 s 有地面预警环
   │
   └─► 场上清空 → CLEARING → 下单典狱长（BOSS_INCOMING，0.9 s）→ BOSS_ACTIVE
                                                             → VICTORY / DEFEAT
```

- **没有曲线、没有并发上限、没有超时兜底。** 批数与每批只数就是 `DIRECTOR.batchSizes`，**总数是它的和（30）**——同一个和同时是"这一局有多少潜袭者""导演可以在途多少""`World` 放行队列的天花板"三个读数（§4.29）。旧曲线时代的 `maxConcurrentSmall`（14）放进 5/5/5/5/10 的脚本里**会把第三批（15 只）剪掉**，所以它被**删掉**而不是调大。
- **典狱长只由"清场"解锁，且只解锁一次**：卡关的玩家不会被超时兜底救出来——**不杀最后一只潜袭者就永远见不到 Boss**，这两半都是设计（§4.30）。清场那一刻 `field:cleared` 顺手把投掷充能补到 `ITEMS.chargesPerClear = 1`，这是整局唯一一次补给。
- **投放点选择**：在环形候选点中筛选，要求距玩家 12–40m、彼此间隔 ≥3.5m，且不在玩家视野正前方 60° 锥内——**绝不允许在玩家脸上刷怪**。

## 2. 技术基线（已核实，勿凭记忆改版本）

| 层 | 选型 | 版本 |
|---|---|---|
| 3D 引擎 | Three.js（**原生，不用 React Three Fiber**） | `0.186.0` |
| 语言 | TypeScript（strict 全开） | `7.0.2` |
| 构建 | Vite（Rolldown 内核） | `8.3.0` |
| 桌面壳 | Electron + electron-builder | `44.3.0` / `26.15.3` |
| 空间查询 | three-mesh-bvh（阶段 4 按需引入） | `0.9.15` |
| 测试 | Vitest | `5.0.0` |
| 资产压缩 | @gltf-transform/cli | `4.5.0` |

Node 基线 **≥ 22.15.0**（`package.json` 的 `engines`；Vite 8 本身只要 ≥ 22.12，但这道坎是 `tests/preload.mjs` 的 `module.registerHooks`——**v22.15.0 才引入**）。

**不引入物理引擎**（Rapier / cannon-es）。理由：击中判定是权威射线查询，不是刚体接触反推；角色控制器无论如何都要自己写。唯一的刚体需求（投掷物抛物线）用解析弹道积分，20 行代码且完全确定可回放。

**不用 React Three Fiber**。R3F 的心智模型是"状态驱动的声明式渲染"，而射击游戏需要"固定步长确定性模拟 + 每帧插值渲染"。把 60Hz 模拟塞进 React 调度器，会导致 `useFrame` 与 `setState` 时序不可控、命中判定无处安放。

升级 `three` 时 **`@types/three` 必须同步升级**（版本号一一对应），并回归验证 `AnimationMixer` 混合行为与 `Raycaster` 层掩码。

## 3. 硬规则（代码评审的判据）

违反以下任意一条，PR 应被驳回。完整说明见 `docs/PROJECT_TECHNICAL_PLAN.md` §2.2 / §4.1。

### 3.1 分层边界

1. **`src/game/**` 不得 import Three.js 的渲染类**（`Mesh` / `Scene` / `WebGLRenderer` / `Material`…）。允许 `Vector3` / `Quaternion` / `MathUtils` 这类纯数学类型。
2. **`src/render/**` 不得包含游戏规则判断**（不能出现"如果血量小于 0"这类逻辑）。
3. **只有 `src/main.ts` 允许直接接触 `document` / `window`。**
4. 模拟层每 tick 输出**纯数据状态**；表现层读取状态并插值到 `Object3D`。

> 这条约束的回报：`enemies/ai.ts`、`combat/damage.ts`、`director/deployment.ts` 全部能在 Vitest 里纯数据驱动测试，不需要 WebGL、不需要浏览器、不需要 mock Three.js。**破坏了它，可测试性立刻归零。**

### 3.2 数值单一真源

**所有**可调数值集中在 `src/core/config.ts`，任何地方**不得出现魔法数字**。

```ts
// ✗ 禁止
if (enemy.health <= 0) enemy.speed = 5.2;

// ✓ 必须
if (enemy.health <= 0) enemy.speed = ENEMY_SMALL.moveSpeed;
```

理由：平衡性调整必须能在一分钟内改完并验证。数值散落在 20 个文件里，这件事就永远做不完。

### 3.3 固定步长不可破坏

- 模拟一律走 `core/loop.ts` 的 `step(fixedDelta)`，**绝不在渲染回调里积分**。
- **所有与时间相关的量必须乘 `dt`**。任何 `x += 5` 形式的逐帧累加都是 bug（会在 144Hz 屏幕上快 2.4 倍）。
- 射速用**累加器**（`fireCooldown += 60 / rpm`）而非赋值，避免浮点误差累积导致射速漂移。
- **命中停顿（hitstop）用模拟时间缩放实现，绝不用"跳过 N 个 tick"**——后者会破坏累加器，停顿结束后出现时间跳变。

### 3.4 随机必须可播种

禁止直接调用 `Math.random()`。一律使用 `core/math` 中可播种的 `Rng`。这既是可测试性的要求（同种子同序列），也是将来做回放/演示的基础。

### 3.5 对象池

弹道曳光、命中贴花、枪口火光、爆炸粒子、伤害数字**必须走对象池**。"每发子弹 new 一个 Mesh"是掉帧的头号原因。**音频的声源节点也是短生命周期对象**（比 Mesh 更贵）——`mixer.ts` 用常驻声部池 + 并发上限，短命节点在 `onended` 里 `disconnect`。

### 3.6 音效只订阅事件（阶段 4）

音频是**表现层**：它订阅 `core/events.ts` 的事件，**绝不接受模拟层的直接调用**，也**绝不**把发声攒到渲染帧（回调发生在产生该事件的同一 tick 内，攒一帧会引入最多 16.7 ms，正好吃掉 SFX ±1 帧的容差）。**不要为了"让音效更准"而往 `src/game/**` 加回调或加事件**——那会立刻破坏"模拟层零渲染依赖"这条规则。全部音频数值（含 23 条合成配方）在 `config.ts`，**零音频文件**。

### 3.7 美化不得改变玩法几何（阶段 4）

`game/level.ts` 的 `props` 同时派生**视觉 / `collisionBoxes` / `blockers`**，改它就等于改玩法空间，**改完必须跑碰撞断言**（`tests/level.test.ts`）。**`Decor` / `level.decor` 从阶段 6 起同样是实体**（尺寸真源是 `DECOR_SPECS`，26 个盒子同时进两个列表；长条障碍物必须在刷怪带之外——见 §4.19）。也**不要**把围栏的 `blocksShots: false` "顺手"改成 `true`（挡人不挡子弹是刻意的）。

## 4. 已知陷阱（都是会静默失败的坑）

### 4.1 `Object3D.layers` 不被子节点继承 ★

> 本条**从阶段 2 起真正生效**（`render/models/CharacterLoader.ts` 与 `render/models/enemyView.ts` 都在建模）。同时注意：**模拟层的命中判定始终是解析式的**（`core/math/intersect.ts`，射线对 AABB / 球），`layers` 只影响渲染侧拾取。所以"敌人打不中"永远不是 `layers` 的问题，"调试面板点不中敌人"才可能是。

对从 GLTF 加载的角色模型，**在根节点上设层是无效的**——必须在 `traverse()` 中逐个 mesh 赋值。这是"射线检测只在 layer 0 生效"的根因。项目里这条已经由 `tests/characterLoader.test.ts` 钉住：断言每一个 mesh 都在 `LAYER_HITTABLE` 上，且 `model.root` **不在**上面。

```ts
model.traverse((o) => {
  if (!(o as Mesh).isMesh) return;
  o.layers.disableAll();
  o.layers.enable(LAYER_HITTABLE);   // 每个子网格单独设置，无一例外
  o.userData.hitZone = inferZone(o); // 'head' | 'body'
});
```

### 4.1.1 状态里"两个都对的判据"要选对（阶段 2 的两个实测 bug）★

这两个 bug 是同一类：状态里存在两个看起来等价的判据，选错的那个只在特定时序下暴露。**改这两处时不要"顺手改回去"。**

| 场景 | 错判据 | 对判据 | 后果 |
|---|---|---|---|
| 回收死掉的敌人 | `if (!enemy.alive) continue;` | `if (enemy.health > 0) continue;` | `applyDamage` 在血量归零的**同一 tick** 就把 `alive` 置 false，于是这个 `continue` 跳过每一具尸体：条目**永远不回收到池子**，`entries` 与 id 表**随击杀数无界增长**，每次命中查询都要多遍历一批死条目。**注意别把它说成"子弹会被尸体吸收"或"槽位被占"——那两条都不成立**（`hitscan` 会 `if (!target.alive) continue`，两个计数也只数 `alive`，而 `releaseSlot` 在置 `alive = false` 之前就调了）；真正的后果是**无界增长 + 条目不回池 + 视图与数组长度脱节**，而这正是下面第二行那个 bug 的温床 |
| 表现层给敌人分配网格 | 按**数组下标**与已建好的 body 配对 | 按**种类**认领 | 模拟层的数组在死亡时"末尾换入空位"紧凑化，下标一错位视图就判定"类型不匹配"，释放旧 body 再新建一个——而释放的那个因类型不同也不会被复用，于是**池子无限增长**，"每帧 new 一个 Mesh"以更隐蔽的形式回来了 |

教训：**表现层不要依赖模拟层数组的下标稳定性**（那是实现细节），**"活着"与"有血"在死亡那一 tick 不是同一个问题**。**写纪要时必须回源码确认后果**——上面第一行的后果曾被写夸张（"子弹被尸体吸收"），夸张的文档会让下一个读它的人按错误的症状去排查。

> **同一族的第三个（C1，低危，未修）**：`World.tick` 的清理循环用**正序** `for...of` 遍历 `enemies.targets` 并在循环里 `despawn`，而 `retire` 是"末尾换入空位"的 O(1) 删除 → 可能**跳过**一个死条目。被跳过的条目 `alive` 已 false，命中查询与计数都不受影响，只是多留一 tick。**`reset()` 用的是倒序**，改的时候照它写；`retire()` 里"nothing iterates it positionally"这句注释目前是错的。见主文档 [§5.8.2](../../../docs/PROJECT_TECHNICAL_PLAN.md#582-清理循环正序遍历会跳过条目c1低危读码结论)。

### 4.1.2 `ATTACK_SLOTS` 的公平性按"完成攻击数"轮转 ★

小敌人的并发近战槽位（`ATTACK_SLOTS = 3`）轮转时，**公平性度量必须是"完成的攻击数"（`served`），不能是"被拒次数"**：被拒次数只在被拒时自增、在释放时清零，于是拿不到槽位的敌人永远攒不起优先级，而拿到槽位的一释放就把自己的计数抹平——饥饿是必然的。另外两处配套：**每一个在攻击距离内的敌人都要调用 `claim()`**（在入口预筛会让落选者根本不累积 `waitingSince`），以及**被中断的攻击用 `release(id, false)` 不记完成**（id 跟着池子走，给中断记完成等于让"死掉"变成下一世的插队券）。三个根因叠在一起才会显形，详见主文档 [§5.7.2](../../../docs/PROJECT_TECHNICAL_PLAN.md#572-槽位轮转的三个叠加根因)。

### 4.1.3 表现层的"每帧重建"要用缓冲，不要用 `Set`

`enemyView` 曾经每帧 `new Set()` 来标记哪些 body 已被认领。在 60Hz 下这是每秒 60 个短命集合。改成"帧末仍未被认领即尸体"的两趟扫描即可。**同类写法都要留意**：任何在 `update()` 里 `new` 出来的容器都是潜在热点。

### 4.2 玩家射线必须排序且同时包含关卡几何

`raycaster.intersectObjects()` 已按距离升序返回，取 `hits[0]`。但**静态关卡几何必须放进同一层**，否则会出现"隔着墙打到敌人"。5m 处的墙永远要赢过 9m 处的敌人。

### 4.3 右键开镜必须屏蔽 `contextmenu`

不阻止的话右键会弹出系统菜单。`core/input.ts` 已处理，改动输入层时不要删掉。**阶段 9 升级**：监听要挂在 `document` 上（只挂 canvas 会让菜单从"指针未锁定"的遮罩 / 暂停面板里漏出来），完整规则见 §4.27。

### 4.4 指针锁定边界必须清空按键状态

Esc 解锁或窗口 `blur` 时清空所有按键。否则会出现"松开 Esc 后角色自己往前跑"的经典 bug。`core/input.ts` 已处理。

### 4.5 长帧必须钳制

标签页切回来时 `performance.now()` 的差值可能是好几秒。`SIM.maxFrameDelta` 与 `SIM.maxStepsPerFrame` 已在循环里处理——**不要为了"更精确"而移除它们**，那会导致死亡螺旋式卡死。

### 4.6 攻击抬手时间不可压缩

不论是狂暴阶段还是"让 Boss 更难"的调整，**抬手时间（telegraph）是玩家唯一的反应依据**。要加难度就压缩收招和冷却，绝不压缩抬手。否则"难"会变成"不公平"。

### 4.7 不要在敌人脸上刷怪，也不要刷在围栏外 ★

投放点必须做**四项**筛选，**顺序不能换**：

1. **在场地内**（`ARENA_HALF_SIZE = 24` 减去 `DIRECTOR.spawnFenceMargin` 留白）；
2. 距玩家 12–40m；
3. 不在视野正前方 60° 锥内（半角 30°）；
4. 彼此间隔 ≥3.5m。

**边界永远是第一道，也是唯一永不放松的一条**：候选环是以**玩家**为心画的，而玩家出生在 `(0, 0, 8)`——以玩家为心的 18m 环在 z 正方向直接到 `26 > 24`，**已经在围栏外**。先按距离筛再夹边界，会把候选点挤到围栏线上（距离条件作废）；不夹就是把敌人刷到场地外。兜底时**反向逐条放宽**（先松 4，再松 3，最后才松 2 的下限），**永远不放松第 1 条**，也永远不允许"刷不出怪"。

**实施时的做法比这个描述更强，照它写**（`spawnPoints.ts`）：**先取随机方向，再算出该方向在场地上实际可达的距离**，把距离采样夹在"配置区间 ∩ 可达区间"里。于是每个候选点**天生在场地内**，不需要"先筛后夹"，角落站位也不会退化成"几乎无解"。**"候选环半径"因此不是可调参数**——它是算出来的。

> ⚠️ **`minSpawnDistanceFromPlayer` 是 12 而不是 Brief 写的 14**，这是从几何算出来的、不是调出来的：出生点 `(0,0,8)` 处"同时满足 14m 且在场内且不在正前方 60° 锥内"的方向几乎不存在，唯一可行的一段就在正前方（也就是被锥排除的那一段）。12 让每一批都真的选得出来，而不是每批都走兜底。详见主文档 [§5.9.2](../../../docs/PROJECT_TECHNICAL_PLAN.md#592-d13一局的终点与波次结构选-a)。

### 4.8 导演必须自己派生一路 `Rng` ★

`World` 里那路 `rng` **已经给了射击求解**（扩散每发消耗两次随机数）。导演若与它共用，**投放点就取决于玩家这一局开了多少枪**——同一份种子会给出两份日程，"同种子同序列"直接碎掉。现在导演用的是 `seed ^ 0x51ed`（照 `createWeaponState(seed ^ 0x9e37)` 的写法）。`tests/world-run-loop.test.ts` 里有一条断言专门钉住"开不开枪都不影响投放点"。

**每局种子**：`main.ts` 现在生成一次 `Date.now() >>> 0` 传给 `createWorld`，并显示在 `F3` 面板（连同 `batch x/5 · alive N · left M` 与 `seed`）。**`Rng` 本身仍然必须可播种**——这与"种子每局换"是两件事。

### 4.9 "已下达、还没出现"的投放仍然算数（并发上限本身已被删除）★

阶段 3 的 `maxConcurrentSmall` 是曲线时代的"压力上限"，而它只看 `smallAlive` 是**不够**的：一条已下达、预警还没走完的投放，在 `smallAlive` 里不可见。投放预警是 0.9s，足够导演在一个窗口里把**整批**都下达出去，上限形同虚设。当时的修法是导演自己记 `inFlightSmall`（下达 +1，`confirmSpawn` / `abandonSpawn` 时 -1），**`World` 在真正 `spawn` 之前再兜一道闸门**。

**阶段 10 把那个上限整个删掉了**（5/5/5/5/10 的脚本里，14 只的上限会把第三批的 15 只剪掉，§4.29），但**那笔记账留了下来，而且换了主人**：`inFlightSmall` 现在是"清场"判据的一部分——判断"这一批放完了"仍然**不能只写 `smallAlive <= 0`**（玩家在每个小敌人出现的那一 tick 就把它打死时，`smallAlive` 在整个投放窗口里一直是 0），条件是三个一起：`smallAlive <= 0 && inFlightSmall <= 0 && spawnedSmall >= plannedSmall`。`World.releaseDueSpawns` 那道闸门的天花板也从 14 换成脚本的和（`totalSmallEnemies()`）。**这是 §4.1.1"两个都对的判据"的第三次出现**：判断"放完了"永远不能只看活体数。见主文档 [§5.9.3](../../../docs/PROJECT_TECHNICAL_PLAN.md#593-双判据与并发上限director-只产出意图但自己记账)。

### 4.10 表现层：同一 slot 上"两个都对的判据"也不要合并 ★（阶段 4 实测 bug）

`enemyView` 的 body slot 现在有两个字段，**答的是两个问题**：`claimed`（这一帧有没有人认领它）与 `deadSince`（它是不是一具正在倒下的尸体）。阶段 4 之前只有 `deadSince`，而 `acquire()` 会把 `deadSince` 清成 `null` 再交出去，收尾循环又用 `deadSince === null` 判"这是尸体" → **每一帧、每一个活着的敌人都会被当成尸体**：活体被反复施加一个 1.1° 前倾又被下一帧抹平（截图看不出来），阶段 4 加上"尸体不投影"之后升级成**所有活体都不投影**。**这是 §4.1.1 那条教训的第四次出现。**

> 另一个附带的教训：**"一条断言通过"不等于"它测的那件事是对的"**——`views.test.ts` 里"尸体播完才复用"那条老断言当时是绿的，因为"活体也被当成尸体"恰好让它的两条要求更容易成立。

### 4.11 表现层的 `update()` 里不得凭空 `new` ★

容器、对象字面量、`Set` 都算。阶段 4 审计出 `main.ts` 的 `collectImpactMarkers()` **每帧每个落点标记 new 一个对象**（一波轰炸 ≈ 每秒 180 个短命对象），改成池化复用。**每次改表现层都自查一遍**：60Hz 下每秒 60 个短命容器就是每秒 60 次 GC 压力。`enemyView` 早期的每帧 `new Set()`、`throwableView` 的两趟扫描都是同一类修正。

### 4.12 不留"改了没用"的旋钮 ★

`RENDER.fogNear` / `fogFar` 曾经在表里、在代码里、在文档里都被当作生效数值，而真正生效的是 `sceneRig.ts` 里硬编码的 `FogExp2` **密度**——改那两个数字**不会改变任何画面**，下一个人会为它花时间。阶段 4 已改成 `RENDER.fogDensityPerArenaSpan` 并由 `tests/scene.test.ts` 钉住"改配置 → 派生值真的变"。**新增任何可调项，要么真的接线并被测试钉住，要么不写进表。**

### 4.13 没有读数就不调数值 / 不开效果 ★

阶段 4 的纪律：**`PLAYER` / `CAMERA` / `WEAPON` / `ENEMY` / `WARDEN` / `DIRECTOR` / `ITEMS` 与阶段 3 逐字相同**（没有真人试玩 = 没有调参依据），D3 的 Bloom 也因缺真机帧率读数而"先不做"。**"没有读数的调参等于换一个随机数"**；反过来，任何"更好看"的改动都要先拿到"它值多少 ms"的数字。

### 4.14 编辑文件不要用 PowerShell 往返 ★（环境）

`Get-Content` / `Set-Content` 在 PowerShell 5.1 下按 ANSI 往返，会**写坏多字节字符**（阶段 4 实测把 `enemyView.ts` 的一个 `—` 写成了 `E2 80 3F`，文件随即不是合法 UTF-8）；`tests/waves.test.ts` 里也有 3 处历史损坏。**一律用编辑工具改文件**；源码与测试文件**只写 ASCII**（硬规则 12 的由来）。发现文件不是合法 UTF-8 时先修编码再改内容。

### 4.15 静态标记会冒充"启动完成"：失败必须落在屏幕上 ★（阶段 5 收尾的现场缺陷）

**现场报告**：`npm run preview` 打开 Web 端后**只有一个写着"箱庭射击"的蓝色页面和一个音量滑条，点击毫无反应**。

根因是一类**静默失败**，`#boot-veil` 是 `index.html` 里的**静态标记**（标题 / 按键行 / 音量面板全在 HTML 里），脚本只负责改文案和藏起它。于是下面两种情况的**画面完全一样**：

1. **脚本根本没执行**（例如拿不到 WebGL2）——`bootGame()` 在 `veil.addEventListener('click', …)` **之前**就抛了；
2. **脚本正常，但浏览器拒绝了指针锁定**——而 `requestLock()` 当时写的是 `result.catch(() => undefined)`，**把拒绝原因当场吞掉**：无事件、无日志、无画面变化。

三条不能改回去的约定：

- **静态文案不得承诺页面还没做到的事**：`#boot-cta` 在标记里必须是 `正在载入…`，真正的"点击画面开始"只由 `main.ts` 写入。**改回静态的"点击画面开始"= 重新挖开这个坑**（`tests/shell.test.ts` 钉住：这句话只允许出现在 `main.ts`）。
- **失败必须有出口**：`showBootProblem()` + `window.onerror` + `unhandledrejection` + `bootGame` 外层 `try/catch`，全部写进 `#boot-warn`（`role="alert"`）。**新增任何可能失败的启动步骤，都要问一句"它失败时玩家会看到什么"**。
- **指针锁定的拒绝必须上报**：`InputState` 的第三个参数 `onLockError` 是唯一通道（Chrome 的 promise 拒绝 + `pointerlockerror` 两条来源）。**不要退回到"吞掉拒绝"**——指针锁定被拒就是死路，玩家必须被告知原因（iframe 需要 `allow="pointer-lock"`）。

> **为什么之前没人抓到**：**Web 端从来没有被"跑"过**。阶段 5 对 Web 侧的验收只有 HTTP 200 + 体积 + 静态引用扫描，**没有一个环节执行过那个页面**；Electron 端实机的指针锁定是成功的，失败路径没有断言。新门槛断言 `bootScriptRan(ctaText)` 就是补这个洞：遮罩上还写着 `正在载入…` ⇒ 模块从未执行 ⇒ FAIL。完整记录见主文档 [§5.13](../../../docs/PROJECT_TECHNICAL_PLAN.md#513-收尾补丁现场反馈点击后没有任何反应静默失败已修)。

### 4.16 测试替身不得比生产实现更宽容 ★（同一现场的**真因**）

**现场第二报**：红字 `启动失败：Cannot read properties of undefined (reading 'handlers')`。真凶是 `src/platform/audio/attach.ts` 里的

```ts
const on = events.on as unknown as (...) => () => void;   // ← 方法脱离了 bus
```

**`const f = obj.method` 是定时炸弹**：方法被摘下来之后就没有接收者了，而 **ES module 恒为严格模式**，`this` 是 `undefined` → `this.handlers` 直接炸。`attachAudio()` 在 `bootGame()` 里排在注册遮罩点击监听**之前**，所以整个游戏启动即死、遮罩永远等不到点击——**这才是"点击没反应"的真因**。修法：`events.on.bind(events)`（或写成闭包）。

> ⚠️ **为什么它活过了两个阶段**：`attachAudio` 是**唯一把总线接到混音器的"接线"模块，而它零覆盖**——`tests/audio.test.ts` 那 33 例全在测 `triggers` / `synth` / `mixer` 这些纯函数。更要命的是：**一个手写的 `{ on: (name, fn) => … }` 替身不具备"方法需要接收者"这个性质**，所以替身能过、真类会炸。
>
> **两条写进约定的教训**：① **凡是接线 / attach / subscribe 这类模块，至少要有一条用真实 `EventBus` 驱动的测试**（`attachAudio` 的 4 例就是这么补的，而且已验证它们在旧代码上 4 条全红、报的就是那句话）；② 看见 `const f = obj.method` 就当成 bug，除非该方法是箭头属性或已被 `bind`。完整记录见主文档 [§5.14](../../../docs/PROJECT_TECHNICAL_PLAN.md#514-现场反馈的第二条启动即抛脱绑定的方法调用点击没反应的真因)。

### 4.17 运行时资产 URL 必须是相对的 ★（S7：想挂成一个网址时才会暴露）

现场提问："能不能有个不用起终端、点开网址就玩的 Web 端？我可以去 GitHub Pages 上申请个子域名。"**答案是可以**——产物是纯静态的、`base: './'` 让引用全相对（详见主文档 [§5.15](../../../docs/PROJECT_TECHNICAL_PLAN.md#515-web-上线一个-dist-挂到-github-pages) 与 [`docs/交付说明.md`](../../../docs/交付说明.md) §2.5），落在仓库里的就是 `.github/workflows/deploy-pages.yml`。

**但顺手抓到一个只在"换挂载点"时才暴露的缺陷**：`PLAYER_MODEL_URL` 原本是绝对路径 `/assets/models/player/player.glb`，三种挂载形态里只有一种是对的：

| 页面位置 | `/assets/…` | `./assets/…` |
|---|---|---|
| 用户站 `https://<user>.github.io/` | ✅ | ✅ |
| **项目站** `https://<user>.github.io/<repo>/` | ❌ 指向**域名根**（不是这个仓库） | ✅ |
| 桌面壳 `file:///…/dist/index.html` | ❌ 指向**盘根** | ✅ |

> ⚠️ **它错得不会响**：`CharacterLoader` 的契约是"模型缺失就退到程序化占位体"，而 `public/` 至今不存在——于是"路径写错"与"资产本来就没到货"**画面完全一样**。这是 §4.1.1"两个都对的判据"那一类问题的镜像：**两个地址都"看起来对"，错的只在特定挂载点暴露。**
>
> **约定**：运行时资产一律相对（`./assets/...`）；`tests/shell.test.ts` 钉住"不得写成 `/assets/...`"。另外**不要为了上 Pages 去改 `base` 或加 `--base`**——相对引用本来就是子目录安全的，改了反而让桌面端黑屏（§4 的 `base` 那条陷阱）。

### 4.18 没人调用的折叠 = 没有这个功能 ★（阶段 6 的现场反馈：视角不随鼠标）

现场第 2 条反馈是"**视角可以随鼠标移动**"——它听起来像一句功能请求，实际是**一个从发布起就存在的致命缺陷**。

`InputState` 的设计是：`mousemove`（指针锁定中）累加进 `pendingLookX/Y` → **由一个单独的 `update()` 把累加值折进"本 tick"** → `sample()` 读它 → `endTick()` 清零。而 `main.ts` 的每步循环只写了 `input.sample()` 与 `input.endTick()`——**`input.update()` 在整份 `src/` 里一次都没有被调用过**。于是 `lookDeltaX / lookDeltaY` 恒为 0，`tickPlayer` 里那句 `state.yaw -= lookDeltaX * lookSensitivity` **永远不减任何东西**：玩家能走、能开枪、能换弹，但**只能朝出生方向看**。

**为什么 467 个测试全绿**：每一个读 `lookDelta` 的测试都**自己手搓 intent**（`world.test.ts` / `world-wave-loop.test.ts`〔阶段 10 改名为 `world-run-loop.test.ts`〕/ `camera.test.ts`），而唯一实例化 `InputState` 的 `input.test.ts` 当时只测指针锁定的失败路径。**没有任何测试同时用到"`InputState` + `sample()` + 位移"这三样**——缺陷不在任何被测函数里，而在"**谁调用谁**"上。这与 §4.16 的脱绑定方法调用是同一类事故的第 2 次。

**约定（写进硬规则）**：

1. **能由调用方"记得调一下"的折叠，一律不要做成独立方法。** 现在折叠在 `sample()` 内部，`update()` 与 `tickLookX/Y` 一并删除——**读到 intent 只有一条路，而那条路必然带着本 tick 的全部鼠标位移**，这个错误在结构上不可表达。`tests/input.test.ts` 的 4 条断言按"**不调用任何其它方法**就能读到位移"写，因为那条"其它方法"就是缺陷本身。
2. **接线类模块必须用真实对象测一次**（§4.16 的同一条）：至少一条断言要跨过"生产调用点"那一层。
3. **多步一帧仍然正确**：第一步拿走全部位移，后续步读到 0——`endTick` 才是消费点，不是 `sample`。

### 4.19 装饰物也是实体，且长条障碍物不得横在刷怪带里 ★（阶段 6 的现场反馈：障碍物没有碰撞）

现场第 3 条反馈是"**游戏里所有的障碍物都增加实体和碰撞效果**"。能穿过的那些（灯柱 / 天线 / 货箱堆 / 管路）不是 bug 而是**阶段 4 的一个刻意决定**：`decor` 通道被排除在碰撞世界外，`tests/level.test.ts` 当时甚至有一条断言**钉着**"decor 不在两个碰撞列表里"。理由（"美化不该悄悄改玩法空间"）站得住，但换来的东西更糟——**看得见的金属管路走进去什么都没有，那读作"游戏坏了"**。

**约定**：

1. **尺寸只有一个真源**：`game/level.ts` 的 `DECOR_SPECS`。`levelView.ts` 用它造网格，`decorCollisionBoxes()` 用它造碰撞盒，**不要再把尺寸写进视图**（那正是网格与碰撞盒开始漂移的起点）。
2. **装饰物同时进 `collisionBoxes` 与 `blockers`**（26 个新盒子：8 灯柱 + 3 天线 + 4×3 货箱 + 3 管路）。围栏的 `blocksShots: false` 仍是**唯一**刻意的例外。
3. **长条障碍物必须在刷怪带之外**——这条只对 AI 成立，因此最容易漏：敌人没有寻路（只有 seek + 沿最浅轴推出），一条横在刷怪带里的长盒子会在身后割出一条**刷怪点能落进去、却只能沿它滑 30 多米才出得来**的走廊。三条管路因此贴到围栏边（`|坐标| = 23.0`），使它的场内面（22.75 m）落在 `SPAWN_LIMIT`（24 − 2.4 = **21.6 m**）之外。`tests/level.test.ts` 用"盒子在任一轴上完全位于（膨胀了敌人半径的）刷怪方框之外"钉住它——**把管路挪回场上，那条断言立刻红**。
4. **`createCollisionWorld` 只读 `level.collisionBoxes` 这一份**（用"顶面不高于脚底"丢掉地板），不要再从 `props` 另起一份推导。这两份推导在装饰物变实体之前**恰好相等**，之后只有一份会知道这件事。
5. ⚠️ **已知副作用**：装饰物现在也进 `blockers`，所以**相机臂**会把它们当障碍（`clearBoom` 读同一份）。一根 0.24 m 的灯柱挡子弹是物理正确的，但它同样会推镜头。若现场反馈"贴着灯柱走时镜头会抖"，**先改"薄件是否该进 `blockers`"，不要去动 `CAMERA.collisionRadius`**（那是给箱子调的量）。

### 4.20 身体的朝向是表现，不是判定 ★（阶段 6 的现场反馈：转身动作）

现场第 1 条反馈是"**增加转身的动作**"。原先 `main.ts` 只有一行 `character.root.rotation.y = player.yaw + Math.PI`：身体**焊在准星上**——侧向移动时横着平移，转身是瞬间换向；而 `PLAYER.turnRateDegPerSec: 720` 从阶段 1 就躺在数值表里，**没有任何代码读过它**（§4.12 明令不许留这种死旋钮）。

现在的分工，**不要改回去**：

| 角度 | 谁拥有 | 用途 |
|---|---|---|
| `player.yaw` | 模拟层 | **权威**：移动解算、弹道方向、相机——一切判定读它 |
| 身体 yaw（`BodyPose.yaw`） | `render/models/characterTurn.ts` + `characterRig.ts` | 只写进 `Object3D.rotation.y`：按 `PLAYER.turnRateDegPerSec` **限速**追上"移动方向"（站着不动时追相机），并带一点转身倾斜（`bodyTurnBankGain`，上限 9°） |

1. **不要把身体 yaw 接进任何判定**——那会把"转身动画"变成"转身延迟"，而射击游戏最不能有的就是输入延迟。
2. **不要把这几行写回 `main.ts`**：`characterRig.ts` 存在的唯一理由就是"这几行必须能被单测"。留在 `main.ts` 里它们需要一个 canvas、一个 renderer 和一个活的 `World` 才能跑——**那正是 §4.18 那条缺陷得以存活的原因**。
3. **限速而不是阻尼**：720°/s 让 180° 恰好 0.25 s，且 60 Hz 与 240 Hz **逐点相同**；阻尼是渐近的，"多久转完"没有答案。
4. **跨 ±π 必须走近路**（`shortestAngleTo` = `wrapAngle(to - from)`），漏了它角色会绕远路转一大圈。
5. **`CharacterModel.reset()`**：死亡 clip 是故意黏住的（`play` 在死亡保持里拒绝切走，这是对的），所以**重开一局必须显式 `reset()`**，否则角色会以死亡姿势站在场上一整局。

### 4.21 二段跳的"空中那一下"要的是上升沿，而上升沿必须在模拟层里派生 ★（阶段 7 的现场反馈：二段跳）

`PLAYER.maxJumps = 2`。地面起跳仍是**电平触发**（按住 `Space` 落地即再跳，阶段 1 起就是这个手感，别动），但**空中那一下必须是新的按压**——按电平判的话，玩家按住不放时第二段会在起飞后的下一个 tick 就被花掉，他得到的是一个矮了一截的跳。

1. **不要新增 `InputIntent.jumpPressed` 之类的字段**。上升沿由 `PlayerState.jumpHeldLastTick`（上一 tick 的电平）在 `tickPlayer` 里当场派生。理由是 §4.16 / §4.18 的同一条教训：**凡是"调用方记得传一下"的东西，就一定有人不传**；派生在模拟层意味着没有任何调用点可以漏，而且天然帧率无关、跨 hitstop 稳定。
2. **一次按压只换一次推力**：同 tick 内起跳会挡住空中那一下（`jumped` 标志）。顺序反了的话"按一下"等于两段全花完。
3. **记账放在 tick 末尾**：那里 `grounded` 才是本 tick 的最终值。`wasGrounded && !grounded && !jumped` ⇒ `jumpsUsed = max(jumpsUsed, 1)`：**走下台沿消耗起跳那一次**，于是"两次跳跃"就是两次，而不是"一次 + 每次掉落白送"。
4. **落地清零**（在起跳判定之前 `if (state.grounded) state.jumpsUsed = 0`）**且 `resetPlayerState` 要一起清** `jumpsUsed` / `jumpHeldLastTick`。
5. 断言里必须有一条**"按住不放只有一段"**（电平 bug 的判据）与一条**"掉下台沿后只剩一段"**（记账顺序 bug 的判据）——少了这两条，写错了照样全绿。

### 4.22 血条用 `Sprite`，填充只改 `scale.x` ★（阶段 7 的现场反馈：敌人头顶血条）

尺寸真源 `HEALTH_BAR`（宽度 / 厚度 / 头顶间隙，按 `small` / `large` 分列），头顶位置 = `ENEMY_ARCHETYPES[kind].height + topGap`（**不要写死高度**：1.1 m 的潜袭者会被悬空的条盖住，3.4 m 的典狱长会把条埋进胸口）。

1. **不要改成 DOM**：那要每帧每敌人一次投影 + 一次样式写入（违反 §4.11），而且永远不被木箱遮挡。**也不要改成需要相机姿态的 Mesh**：那会给 `enemyView.update()` 加一个 `cameraQuaternion` 参数——又一个"调用方记得传"的口子。`Sprite` 由渲染器自己丢掉旋转、保留世界缩放，**朝向问题在结构上不存在**。
2. **填充从中间对称收缩，只改 `scale.x`、位置恒为 0**。sprite 的**位置**不会被 billboard 化（只有旋转会），所以"把填充往左挪半个身位"在敌人侧对镜头时会横着滑出去。
3. **共面不打架**：槽与填充同一位置，两者 `depthWrite: false`（`depthTest` 保留，箱子照样挡得住），靠 `renderOrder` 1 / 2 决定谁后画；`toneMapped: false` 让红色就是配置里的红。
4. **尸体不留血条**：在"这具身体不再被上报"的那一帧隐藏（与关投影同一帧、同一个判据），槽位复用时恢复。用的仍是 `claimed`，不是 `deadSince`（§4.10）。
5. **池化**：每具身体 2 个 sprite，材质**每个视图一份**（120 敌人 = 2 份材质，不是 240 份），`dispose()` 里**显式回收**——sprite 不是 mesh，走不到那段通用遍历。
6. **已知代价**：120 实体 = **240 次额外 draw call**，而本机没有真机帧率读数。若 `--scene perf` 变差，第一件事是把这对 sprite 换成两个 `InstancedMesh`（渲染层内部改动，不动模拟层）。

### 4.23 枪挂在身体根上，位置只看世界坐标 ★（阶段 7 的现场反馈：右手那把枪）

`render/models/playerWeapon.ts`（程序化几何）+ `WEAPON_MODEL`（尺寸与颜色单一真源：黑握把 / 枪托 / 扳机 / 护圈，暗钢枪管后段，**橙色枪管前段与枪口**）。`characterRig` 把它加进 `model.root`，位置就是 `WEAPON_MODEL.anchor`。

1. **模型局部的"右手"是 `-x`**（模型面朝 `+Z`，右 = 前 × 上），而身体画出来时又被转 `yaw + π`——两处符号一叠，局部偏移看着可以是任一侧。**断言只看世界坐标**："枪在玩家的 +X 侧且在身前（-Z）"，以及"身体转身时它与身体的距离不变"。
2. **不要挂手骨**：`player.glb` 从未交付，手骨的名字 / 朝向 / 缩放没有实物可对，一个没法端到端验证的骨骼偏移只会在资产到货那天变成"枪长在胳膊里"的静默 bug。当前挂点对"1.75 m、脚在原点、面朝 `+Z`"的任何模型都成立（Brief 的接入约定）；肩宽不同就改 `anchor` 一个数。
3. **它不负责枪口**：曳光起点是模拟层的 `World.muzzlePosition`（相机基座上的 `CAMERA.muzzleSide` / `muzzleDrop`）。让枪模再报一个枪口就是同一个问题的第二份真相，而且那个点决定"子弹先打到什么"，属于玩法。**已知不完美**：枪口比曳光起点靠前约 0.7 m，从背后看是"火光在肩侧、枪口在前方"——要修得先决定"枪口偏移是否属于玩法"。

### 4.24 全屏层只有三块，暂停有自己的层 ★（阶段 7 的现场反馈：`Esc` 不要直接回起始界面）

面纱（`#boot-veil`）是**一个元素兼了三种意思**（点击开始 / 暂停 / 结算），`h1` 永远是"箱庭射击"——所以 `Esc` 之后玩家看到的就是那块不透明、长得跟标题页一样的东西，而且**没有任何办法说"重开"或"回主界面"**。

1. **三层**：`veil`（不透明，点击=开始）/ `pause`（半透明 `#pause-menu`，`结束暂停` / `重新开始` / `返回主界面`）/ `hud`。**可见性只由 `render/hud/hud.ts` 的 `overlayVisibility(mode)` 决定**，返回 `{ veilHidden, pauseHidden, hudHidden }`，不变量是"**恰好一层可见，且 HUD 只在一层都没有时才可见**"；`createHud` 的每次切换都走同一个 `applyOverlay()`（幂等）。**不要再往面纱上挂第四种意思**。`VeilMode` 这个 union 也住在 `hud.ts`，与那个函数挨着。
2. **三个按钮的接线住在 `render/hud/pauseMenu.ts`**（拿元素 + 拿三个回调），所以 `tests/pauseMenu.test.ts` 能点真的按钮并断言游戏被告知了什么（含"三个选项互不串线"）。能单测的接线不要留在 `main.ts`（§4.16 的同一条教训）。
3. **被拒绝的指针锁定要报到当前可见的那一层**：暂停时是 `#pause-warn`，不是**藏在隐藏面纱里的** `#boot-warn`。写错地方的后果是"点了没反应、屏幕什么都没变"——正是 §4.15 那条缺陷的形状。（Chrome 在 `Esc` 之后约 1.25 s 内会拒绝一次锁定请求，这条路径真的会走到。）
4. **`重新开始` 先重置世界再请求锁定**：锁定被拒时玩家面对的是一个"暂停中的新一局"，而不是上一局的尸体。

### 4.25 视角是"基座的一种姿态"，而且只有一份真相 ★（阶段 8 的现场反馈：`V` 切换第一 / 第三人称）

`CameraState.viewMode` 是唯一权威（模拟层拥有它，因为**瞄准解算读它**），两种模式的数字全在 `VIEW`（`config.ts`），第三人称那几项与 `CAMERA` 的值**逐条钉住**（`tests/camera.test.ts`）。

1. **`V` 必须走 `World.toggleView()`**：它顺带**重解瞄准**并 snap 相机。**只改渲染相机的实现在画面上"看起来对"，而准星、曳光与命中会在三个地方**。
2. **切换只许改基座位置 / 相机后撤距离 / 曳光起点，绝不许改 `forward`**：两种模式的 `direction` 与 `fovDeg` 必须逐位相同（否则"换个视角子弹就偏了"）。
3. 第一人称的**曳光横向分量是 0**、**不做 boom 避障**；表现层"这个模式画什么"只住在 `characterRig.sync()`。`sync` / `solveAim` 的默认模式是 `thirdPerson`，而游戏默认是 `CAMERA.defaultView = firstPerson`——**这两个默认值不同是故意的**。详见主文档 [§5.19](../../../docs/PROJECT_TECHNICAL_PLAN.md#519-阶段-8-实施纪要第一--第三人称切换)。

### 4.26 准心在 ADS 里必须变大，而扩散锥的投影是反的 ★（阶段 9 的现场反馈：开镜的准心）

`crosshairRadius(spreadDeg, fovDeg, viewportHeight, adsProgress)`（`render/hud/hud.ts`）是唯一的裁决：

1. **腰射环 = 扩散锥的投影**（扳机纪律的读数，阶段 1 起没变）。而 ADS 同时把锥从 3.4° 压到 0.35°、把 FOV 从 78° 拉到 45°，**两个因子一起把环缩成一个点**——所以"开镜准心变大"不是改一个数，而是**换语义**：ADS 环是一个固定尺寸的瞄准具（`CROSSHAIR.adsRadiusPx = 46 px`，`config.ts` 是唯一真源）。
2. **取值是 `max(实时扩散锥投影, 从静止腰射半径线性长到 ADS 环)`，那个 `max` 不许拿掉。** 直接插值会让环**先缩后长**：锥在 0.18 s 过渡的前 0.13 s 就塌了，而插值才走到 1/4。`tests/hud.test.ts` 用武器真实产生的 (spread, fov) 走完 0→1 断言单调，就是为了钉住这一点。
3. **投影只有一份实现**：`game/camera/camera.ts` 的 `spreadToScreenRadius`，由 `hud.ts` 调用（`render/camera/cameraRig.ts` 里那份重复的 `crosshairRadiusPx` 已删除）。**不要再复制第三份**——两份一样的规则里必然有一份先过期。
4. `#crosshair.ads` 那个 class 只在**满 ADS**（`adsProgress >= 1`，与 `weapon.aiming` 同一个边界）时亮，它加粗环并换成 accent 蓝：尺寸是过渡，class 是状态。详见主文档 [§5.20.1](../../../docs/PROJECT_TECHNICAL_PLAN.md#5201-右键开镜的三件事准心变大拉近不吃浏览器菜单)。

### 4.27 右键只在游戏里起作用：两个方向都要守 ★（阶段 9 的现场反馈：右键不吃浏览器菜单）

1. **浏览器侧**：`contextmenu` 的监听**必须挂在 `document`**，不能只挂 canvas。这不是"更保险"，而是一个具体的漏：指针**未锁定**时顶层元素是遮罩（标题 / 结算）或暂停面板，事件目标是它们，挂在 `canvas` 上的监听**根本收不到**——也就是"右键菜单从菜单状态里漏出来"。`tests/input.test.ts` 钉住"挂在 `document` 上、`dispose` 解绑、事件被 `preventDefault`"。
2. **游戏侧**：ADS 仍只在指针锁定时成立——`handleMouseDown` 在未锁定时**只请求锁定、不往 `buttons` 里放任何键**，`sample().aim` 读的是 `buttons.has(2)`。所以"游戏外（标题 / 暂停 / 结算）右键什么也不做"这条自动成立，**不要为它加特判**。
3. **拉近不需要改代码**：`fovDeg` 由 `solveAim` 按 `adsProgress` 插值，`applyCameraState` 每次差值 > 1e-4 就写 `camera.fov` 并重建投影矩阵——所以它是连续变的，不是"到位才跳"。（§4.3 那条"必须屏蔽 `contextmenu`"是本条的子集，已按本条升级。）

### 4.28 攻击的"方向"只在发射那一刻解一次 ★（阶段 9 的现场反馈：典狱长的黄色直线）

典狱长不再做区域轰炸，而是**从自己身上朝玩家射一条黄色直线**。三件事在代码里是硬约定：

1. **`WardenAim` 是"还没发射"的状态**：抬手期间**每 tick 重解**（渲染层每帧拿它画黄线，`aim.active` 就是"还有一条线"），发射瞬间由 `fireShot()` **把方向拷进** `WardenShot.direction`——此后**没有任何代码再写它**。`tests/enemies.test.ts` 用"发射后三个分量逐位相同"钉住。默认瞄的是玩家**当前**位置：旧的 `leadTarget` 预判是给"落在玩家将要去的地面"用的，而一条"指向将来位置"的直线在画面上就是**指着玩家旁边**，比可躲更糟（该函数已随旧设计删除，**不要加回来**）。
2. **命中是"本 tick 的扫掠线段 × 按 `shotRadius` 膨胀过的玩家伤害盒"**（`core/math/intersect.ts` 的 `segmentIntersectsAabb`）：24 m/s 在 60 Hz 下一 tick 走 0.4 m，而玩家伤害盒宽 0.84 m——点采样会让弹丸在两 tick 之间**穿人而过**。同一段线段还过一次 `ctx.collision.solids`（取最近 `t`），所以**躲在货箱后面是安全的**（线的终点发 `enemy:shotEnded{hitPlayer:false}`：画黄色闪光但**不出声**）。
3. **只打玩家**（旧区域轰炸会连自己的小兵一起炸，而"拉小兵进轰炸圈"是玩家的正当收益；弹丸误伤会让"一条线"这套视觉语言不再描述实际规则），并且**弹丸的飞行不绑主人的状态机**：`resolveShots` 对每个活典狱长每 tick 都跑，`SHOT` 状态只持续 `activeTime`。旧设计里 `BARRAGE` 必须等引信烧完**是对的**（区域爆炸绕着主人落），照搬到弹丸上会让主人站着等一枚已经离它而去的弹丸。详见主文档 [§5.20.2](../../../docs/PROJECT_TECHNICAL_PLAN.md#5202-典狱长一条从它自己身上射向玩家的黄色直线)。

### 4.29 一局的脚本是数据，而它的"和"是总数的唯一真源 ★（阶段 10：把曲线换成固定脚本）

1. **日程住在 `DIRECTOR`**（`openingCountdown = 10` / `batchInterval = 10` / `batchSizes = [5, 5, 5, 5, 10]`），**解析器只有一处**：`game/director/deployment.ts` 的 `planDeployment()`——它把每批解析成 `{index, count, at}`，其中 `at = openingCountdown + batchInterval * index` 是**绝对时刻**（与 `ctx.time` 比，不是"上一批之后 10 秒"），所以长帧与 hitstop 只能推迟"什么时候被注意到"，不能改变它属于第几秒。
2. **`drops[].count` 的和就是这一局的小兵总数**，`totalSmallEnemies()` 直接返回解析结果里的那个和；它同时是**三个读数的唯一来源**——HUD 的读数、导演的"在途"上限、`World.releaseDueSpawns` 放行闸门的天花板。**不要再引入第二个"这一局有几十只"的数。**
3. **旧曲线那些数不是被调大，而是被删除**：`maxConcurrentSmall = 14` 在曲线时代是"压力上限"，放进 5/5/5/5/10 的脚本里**会把第三批（15 只）剪掉**；`totalWaves` / `maxConcurrentTotal` / `spawnInterval*` / `smallCount*` / `smallHealthScalePerWave` / `bossTimer*` / `addsWhileBossAlive*` / `breathingWave*` / `interWaveDelay` / `openingGracePeriod` / `DIRECTOR_REWARDS`（并进 `ITEMS.chargesPerClear = 1`）与 `EnemyStore` 的逐次 `healthScale` / `scaledStats` 一起消失。**"每具身体的血量是配置的幂"也不再需要**：30 只潜袭者逐字相同，缩放因子只是一个假装成曲线的常数。`tests/deployment.test.ts`（10 例）钉住脚本本身，`tests/world-run-loop.test.ts`（23 例）钉住它被真正执行。

### 4.30 "下了单"不等于"到场了"——绝不在下单的那个相位里读 `bossAlive` ★（阶段 10 抓到的真缺陷）

1. **事实**：典狱长在下单之后还要走 `DIRECTOR.spawnWarningDuration = 0.9 s` 的落地预警，这段时间里 `ctx.bossAlive` **恒为 `false`**。旧状态机在下单那一 tick 就把相位设成 `BOSS_ACTIVE`，于是下一 tick 就走进"`!bossAlive` ⇒ 场上空了"的分支，**在典狱长自己的落地预警期间宣布整局清场**——探针实测 **53 tick（0.88 s）**，发生在最后一波上就是"Boss 还在路上、玩家已经胜利"。
2. **修法是一个相位，不是一个 `if`**：相位表是 `OPENING / DEPLOYING / CLEARING / BOSS_INCOMING / BOSS_ACTIVE / VICTORY / DEFEAT`，**`BOSS_INCOMING` 就是那 0.9 秒**——身体必须先被**看见**，才可能被错过。
3. **为什么全部测试都是绿的**：旧 harness 的假世界在**下单那一 tick** 就把 `bossAlive` 置真，所以它测的时序**根本不存在于真实世界**。**假世界必须按真实世界的交付时序建模**（身体在预警结束后才出现，导演下一 tick 才看到它），`tests/director.test.ts` 与 `tests/world-run-loop.test.ts` 现在都按这个时序交付。同类教训见 §4.16（测试替身不得比生产实现更宽容）。

### 4.31 世界必须在玩家接管之前停住，否则倒计时和开局都被面纱吃掉 ★（阶段 10 的前置修复）

1. **`bootGame().start()` 必须 `loop.setPaused(true)`**，`t = 0` 是玩家点进来、**指针锁定成功之后**的第一个 tick。在那之前世界从页面加载就开始走：十秒倒计时会被标题页吃掉（点进去可能只剩两三秒），敌人甚至可能在**不透明面纱后面**被刷出来。
2. **暂停不等于不渲染**：循环在暂停时照常渲染（标题页背后的场景本来就是这么画的），所以这条改动**在标题页上看不出任何区别**——它的收益全在点进来之后的那一局。
3. **连带影响**：`npm run desktop:accept -- --scene perf` 现在依赖那次点击真的拿到指针锁定（测量在点击之后才开始），**锁定被拒就会报 0 个实体**——读数异常时先看这一条，而不是先怀疑模拟层。`#countdown` 只在脚本的开局那一段存在（`countdownSeconds > 0`），文案来自 `countdownText()`（`ceil` + 下限 1，`tests/hud.test.ts` 钉住它永不显示 0）。

### 5.1 关键纪律

- **P1 是唯一允许超期的阶段。** 它的产出质量决定 P2–P4 的天花板。如果射击手感自己玩着不爽，**不要往下走**——先把它调到爽。
- **P1 刻意不做敌人**（阶段 2 才接 AI），先做敌人会让手感问题被噪音掩盖。**P1 的手感数值至今仍未经真人试玩定标**——这是唯一一处"阶段已经打勾、数值还没定"的债。
- **资产交付不能阻塞开发。** 人物模型未到位时用程序化胶囊体占位；模型是运行时加载，接入不改代码（`loadCharacter()` 永不 reject，缺 Clip 就沿 `run→walk→idle` 降级并告警）。
- **每个阶段结束跑 `npm run typecheck && npm run test`**，必须全绿。
- **目视验收不能只靠 DOM 断言。** 启动遮罩缺陷就是这么溜过去的：断言写反了，于是"遮罩盖着画面"被验成通过。任何"画面正常"的结论都要有一张截图 + 一条像素断言。
  ⚠️ **阶段 5 补上了这条纪律的另一半**：像素断言必须读**合成后的那一帧**（CDP 的 `Page.captureScreenshot`），不能读 WebGL 画布——渲染器是 `preserveDrawingBuffer: false`，绘制缓冲合成后即被清空，读它**必然读到空白**（这正是那个从阶段 2 起"永远失败"的探针）。同时要分清**"合成了一帧"与"3D 场景画出来了"**：整帧断言 + 一条**不含 HUD 的场景带**断言，两条都要。

### 5.3 阶段 2 / 3 / 4 / 5 / 6 / 7 / 8 / 9 / 10 新增的关键约定（不要改回去）

1. **敌人仓库是单一仓库（路由 A）**：`src/game/enemies/EnemyStore.ts` 取代了 `src/game/targets.ts`；练习靶与新敌人共用一个 `entries` 数组和一个 id 空间，靶子是 `kind: 'dummy'`。**不要再拆成两份可命中体列表**——"5m 的墙永远赢过 9m 的敌人"这条规则只能在一次比较里成立。`World` 上的属性叫 `enemies`，仓库内部的数组仍叫 `targets`。
2. **`player:damaged` 是单向事件**：敌人层只发布伤害请求，`World` 订阅并决定结果（无敌帧、血量夹取、死亡）。敌人层不得引用 `PlayerState`。
3. **`enemy.stats` 是"每个身体一份"的**（阶段 3 修）：`spawn` 用 `{...base, maxHealth: 缩放后的值}` 覆盖到条目上，池化复用同一对象。**不要改回"直接引用 archetype 的共享对象"**——那样 `health` 被缩放而 `stats.maxHealth` 没有，血量条 / 伤害数字 / 硬直阈值 / 狂暴阈值会全部读错，而战斗表现看起来仍然正常。
4. **调试编队已整块删除**：`DEBUG_ENEMIES` / `WorldOptions.debugEnemies` / `spawnDebugWave()` / `main.ts` 的参数**都不存在了**。**不要加回来**：两条"谁负责刷怪"的真相，而且会让清场判据永远不成立。**阶段 4 新增的唯一"制造大量敌人"的入口是 `src/debug/perfScene.ts`（只经 `?scene=perf` 打开，且只调用 `World` 公开方法）**——它同样不是第二条"谁负责刷怪"的真相。
5. **`World.tick` 内部顺序**（阶段 3 后共 10 步）：时间缩放 → 武器 → 玩家 → 投掷 → 瞄准重解 → `enemies.tick` → `enemies.sync` → 射击 → **投掷物积分与爆炸结算** → **清理（倒序，判据是 `health > 0`）** → **导演**。三条承重原因：敌人必须先于射击；爆炸必须晚于 `enemies.sync`（读本 tick 位置）且早于清理（被炸死的走同一条回收路径）；**导演必须晚于清理**，否则 `liveCount()` 会数进本 tick 即将回收的尸体，清场判据与放行闸门都差一 tick。
6. **回收判据是"血量"不是"活着"**（见 §4.1.1）；**表现层的网格分配按种类不按下标**；**清理循环必须倒序**（见 §4.1.1 的 C1）。
7. **`Director` 只产出意图、自己记账**：`tick(ctx, out)` 往 `out` 里追加订单，`World` 执行 `spawn` 并回调 `confirmSpawn` / `abandonSpawn`。**不要把 `enemies.spawn` 写进导演**——那样清场闸门与批次推进就无法在没有世界的情况下单测。
8. **（阶段 4）音效只订阅事件，且在事件回调里立刻发声**：**绝不**把音频接进 `src/game/**`，也**绝不**把发声攒到渲染帧（那会引入最多 16.7 ms，正好吃掉 SFX ±1 帧的容差）。唯一订阅点是 `src/platform/audio/attach.ts`，唯一接触 `AudioContext` 的模块是 `mixer.ts`。**加一声只需在 `SOUND_SPECS` 加一条配方 + 在 `triggers.ts` 的 switch 里加一个分支。**
9. **（阶段 4）音频零文件**：任何 `new Audio()` / `<audio src>` / `fetch('*.mp3')` 都是必然失败的加载（`public/` 不存在），也正是 D12 修掉的假阳性。**全部程序化合成。**
10. **（阶段 4）同一个 slot 上答两个问题的字段不要合成一个判据**：`enemyView` 的 body slot 有 `claimed`（这一帧有没有人认领）与 `deadSince`（是不是正在倒下的尸体）。混成 `deadSince === null` 会让**每个活体每帧被当成尸体**（活体被反复施加又抹平 1.1° 前倾；阶段 4 加上"尸体不投影"后升级成"活体都不投影"）。这是 §4.1.1"两个都对的判据"的第四次出现。
11. **（阶段 4）表现层 `update()` 里不得凭空 `new`**：容器、字面量、`Set` 都算。改表现层时自查一遍（60Hz 下每秒 60 个短命容器 = 每秒 60 次 GC 压力）。`tests/views.test.ts` 有两条断言钉着"重复 update 不新建对象"与"池子稳定在峰值并发数"。
12. **（阶段 4）不留"改了没用"的旋钮**：`RENDER.fogNear` / `fogFar` 曾是死字段（真旋钮是 `sceneRig.ts` 里的硬编码密度）。现在是 `RENDER.fogDensityPerArenaSpan`，并由 `tests/scene.test.ts` 钉住"改配置 → 派生值真的变"。**新增任何可调项都要么真的接线并被测试钉住，要么不写进表。**
13. **（阶段 5）验收断言不得为了让结果变绿而放宽，但"断言测的不是它声称在测的东西"必须修**：阶段 5 改的是**测量对象与分类方式**——像素证据从"读被清空的 WebGL 画布"改成"读 CDP 合成截图"，日志豁免从"只看 `Network` 一条通道"改成"两条通道同一套双向断言"。**阈值与"零容忍"的方向一寸没让。** 加每条新断言都要追问两句：**它失败时画面是什么样？它通过时能排除什么？** —— `requestCount: 0`（连上后未 reload，一个请求都没观察到）就是"通过但什么都没排除"的典型。

<summary>npm 在本机受限沙箱下的注意事项</summary>

本机沙箱默认只允许写入工作区。`npm` 的默认缓存位于 `C:\Users\...\npm-cache`，会被拒绝（`EPERM`）。需要执行 `npm view` / `npm install` 时，显式指定工作区内的缓存目录：

```powershell
npm view <pkg> version --cache .tmp-npm-cache
npm install --cache .tmp-npm-cache
```

- 项目运行环境为 Windows + 受限沙箱
- 禁止要求关闭沙箱或授予危险权限
- 所有测试必须在沙箱约束下通过配置解决

**测试运行已经被配置解决了，不要再为此申请提权。** 三个问题、三处配置：

| 症状 | 真实原因 | 解决位置 |
|---|---|---|
| `failed to load config` / `spawn EPERM` | Vite 在 Windows 上首次解析真实路径时会 `exec('net use')` 探测网络驱动器，子进程被沙箱拒绝 | `tests/preload.mjs` 劫持 `child_process.exec/execFile`，对 `net use` 返回空结果（等于"没有网络驱动器"，也就是本机真实情况） |
| `Failed to start forks worker` | Vitest 默认用 fork 进程池，等于再 spawn 子进程 | `vitest.config.mjs` 里 `pool: 'threads'` |
| `Cannot find module '@/core'` / 无扩展名导入 | Node ESM 要求扩展名，不会像打包器那样推断 | `tests/preload.mjs` 注册 ESM resolve hook；`package.json` 的 `imports` 提供 `#/*` → `./src/*` |
| `NODE_OPTIONS` 传不进脚本 | Windows npm script 不能写 `VAR=x cmd` | 项目根的 `.npmrc` 用 `node-options=` 注入 |

`npm test` 因此开箱可用（`preload.mjs` 由 `.npmrc` 自动预加载）。**测试文件用 `#/...` 导入源码**：这是 `package.json` 的 `imports` 映射，Node 原生支持；`@/...` 只有打包器认识，Node 直跑会失败。

### 桌面端在沙箱里跑不起来（不是 bug，也没有配置解）

**任何 Electron / Chromium 进程**在受限沙箱下都会死在命名管道上：

```
FATAL:mojo\public\cpp\platform\platform_channel.cc:108] Check failed: . : 拒绝访问。 (0x5)
```

`--no-sandbox`、`--single-process`、`--in-process-gpu`、`--disable-gpu` 及其组合**全部在同一处失败**——已逐一验证过，不要再花时间试开关。`electron-builder` 同理：它的 node-module collector 会 `spawn` 一个 `npm list` 子进程，`spawn EPERM`，且没有开关可跳过。

| Electron 二进制 | 已下载（`44.3.0`）。注意 **Node 的 TLS 可用、schannel 不可用**：`curl.exe` / `Invoke-WebRequest` 会报 `SEC_E_NO_CREDENTIALS`，那不是"没网" |

13. **动过相机 / 加了一个"模式"吗？** 模式只能住在模拟层的那一份状态里（`CameraState.viewMode`），切换必须走 `World.toggleView()`（翻转 → 重解瞄准 → snap）；**任何"只改渲染相机"的写法都会让准星、曳光与命中各说各话**。表现层的模式判断只允许住在 `characterRig.sync()`。**加断言时问一句：它失败时画面是什么样？它通过时能排除什么？**（§4.25 / §5.3 第 13 条）

16. **动过投放日程 / 胜负判据 / 启动流程吗？** 批数与每批只数只认 `DIRECTOR`，**总数只认脚本的和**（§4.29）；典狱长的闸门**只有"清场"一条**，而且**下单之后要等身体真的出现**才许判它死活（§4.30）；世界在指针锁定之前**必须暂停**（§4.31）。改完跑 `tests/deployment.test.ts` 与 `tests/world-run-loop.test.ts`。
